# Crypto caps agent spending but never adjudicates

As of late October 2026, crypto and stablecoin rails handle AI-agent spending authorization well and "my AI bought that" disputes hardly at all, and nothing found does what Readback does on PayPal rails. On-chain smart accounts (Coinbase Spend Permissions, MetaMask's ERC-7715/7710 delegations, Safe, ERC-7579 session modules) bind a specific agent key into a user-signed grant and enforce caps in contract code, but they record a budget, not an instruction, and every live stablecoin rail settles finally, with refunds after capture left to the merchant. The intent-record standards, AP2 v0.2 and Mastercard's Verifiable Intent, have converged on exactly Readback's shape (a user-approved open mandate that pins the agent's key, then agent-signed closed mandates per purchase), yet both stop before retention and dispute handling, and no card network, PSP, or protocol has an agent-specific dispute rule. PayPal itself has no published agent mandate, is not among x402's named initial supporters, and has no published PYUSD agent rail; its crypto terms treat an agent that overspends as authority the user granted and the agent exceeded, which leaves the user liable until she revokes it, so the deciding facts are the delegated scope and the revocation time, which is the record Readback produces. Crypto therefore sharpens Readback's pitch rather than displacing it, with one exception: on-chain grants survive revocation, while PayPal deletes Maya's agreement within minutes of an unauthorized claim. That weakness is real, and it gives the `agent_terms` proposal its strongest outside precedent.

## On-chain controls cap what an agent can spend, not what Maya meant

Every major smart-account stack expresses an agent's authority as one signer key plus a set of policies, checked by a contract at execution time. Coinbase's **Spend Permissions** is the cleanest case: a nine-field struct (account, spender, token, allowance per period, period, start, end, salt, extra data) held by one singleton contract deployed on Base, Ethereum, and six other chains, which reverts any spend outside the window or over the period's allowance ([SpendPermissionManager.sol](https://raw.githubusercontent.com/coinbase/spend-permissions/main/src/SpendPermissionManager.sol); [coinbase/spend-permissions](https://github.com/coinbase/spend-permissions)). Structurally it is the closest crypto analogue to Readback's recurring-prepaid vault agreement with a per-period cap. Safe's Allowance Module keeps a per-delegate counter; Biconomy/Rhinestone Smart Sessions and ZeroDev Kernel compose policies for contract, function, parameter, value, rate, and time ([safe-modules/allowances](https://github.com/safe-global/safe-modules/tree/main/modules/allowances); [Biconomy](https://docs.biconomy.io/new/smart-sessions/policies); [ZeroDev](https://docs.zerodev.app/sdk/permissions/intro)). **ERC-7715 is still a Draft**, and its wallet method is now `wallet_requestExecutionPermissions`, not the `wallet_grantPermissions` name many 2025 write-ups use; MetaMask ships it in the mainline extension (v13.23.0+) as Advanced Permissions for token allowances ([ERC-7715](https://eips.ethereum.org/EIPS/eip-7715); [MetaMask](https://docs.metamask.io/smart-accounts-kit/concepts/advanced-permissions.md)).

All of these **bind a specific agent key**: Coinbase's `spender` sits inside the signed EIP-712 typehash, ERC-7715 names the session account in `to`, Smart Sessions require a session public key ([SpendPermissionManager.sol](https://raw.githubusercontent.com/coinbase/spend-permissions/main/src/SpendPermissionManager.sol); [ERC-7715](https://eips.ethereum.org/EIPS/eip-7715)). So Readback is not the first to put an agent key inside a user's approval, and §5 should say so. Two differences favor Readback. First, no source shows a wallet displaying the agent's address at approval time; MetaMask documents showing start time, amount, and period only ([MetaMask](https://docs.metamask.io/smart-accounts-kit/concepts/advanced-permissions.md)). Second, none of these schemes binds per-purchase intent: Coinbase's recipient is an argument to `spend()`, not a field of the permission, and Safe allowances don't restrict the recipient at all. A per-purchase signed mandate is a layer they don't have.

Wallet vendors that hold keys for agents enforce limits differently, in a policy engine before signing. Coinbase's CDP policies (accept/reject rules on value and address), Privy's scoped authorization keys, and Turnkey's allow/deny policies all live in the vendor's system, and Turnkey's root quorum bypasses every policy ([CDP](https://docs.cdp.coinbase.com/server-wallets/v2/using-the-wallet-api/policies/overview); [Privy](https://docs.privy.io/wallets/overview/solutions/agent-wallets); [Turnkey](https://docs.turnkey.com/concepts/policies/overview)). Those records are as mutable as PayPal's, and the operator, not the end user, controls them.

The incident record shows why limits don't settle disputes. Signature phishing still cost **$83.85M across 106,106 victims in 2025**, down 83% from 2024 but still the dominant user-side loss ([Scam Sniffer](https://drops.scamsniffer.io/scam-sniffer-2025-crypto-phishing-losses-fall-83-to-84-million/)). On May 4, 2026, a Morse-coded post on X talked Grok/Bankrbot into moving about **$150–200K** of tokens from a verified wallet on Base, exploiting what the agent was permitted to do rather than any contract flaw ([OECD AI Incidents Monitor](https://oecd.ai/en/incidents/2026-05-04-4a73)). Caps shrink the blast radius of that second failure mode, but a spend inside a valid permission is final whether or not the human wanted it. MetaMask's own dispute partner frames the open problem the same way: an agent can stay inside every limit and still violate the user's plain-language mandate ([MetaMask/GenLayer, Sep 25, 2026](https://metamask.io/news/genlayer-internet-court-ai-agent-jury)).

## Intent standards converge on Readback's shape, then stop at the dispute

The protocols split three ways. **Payment-authorization protocols carry no intent.** In x402, the user's authorization is a one-time EIP-3009 or Permit2 transfer signature over amount, recipient, validity window, and nonce; the facilitator can't change amount or destination, and the spec has no mandate, standing delegation, refund, or dispute concept ([x402 exact EVM scheme](https://raw.githubusercontent.com/x402-foundation/x402/main/specs/schemes/exact/scheme_exact_evm.md); [x402 repo](https://github.com/coinbase/x402)). Governance moved to the Linux Foundation's x402 Foundation on Apr 2, 2026, with Coinbase, Cloudflare, Stripe, Google, Visa, Mastercard, AWS, Amex, Shopify, and others listed; **PayPal is not on the list** ([Linux Foundation](https://www.linuxfoundation.org/press/linux-foundation-is-launching-the-x402-foundation-and-welcoming-the-contribution-of-the-x402-protocol)). Usage figures are secondary and contradict each other: Coinbase-reported totals of about 165M transactions and $50M by April 2026 sit beside estimates of about $28K a day in real commerce, with roughly half of activity classed as gamified ([presenc.ai](https://presenc.ai/research/x402-protocol-adoption-tracker-2026)).

**Scoped credentials authenticate the agent or cap the token, not the instruction.** Stripe's Shared Payment Token is scoped to one seller with a currency, max amount, and expiry, and is revocable, but nothing binds it to an agent key or records what the user asked for ([Stripe docs](https://docs.stripe.com/agentic-commerce/concepts/shared-payment-tokens.md?agent-seller=agent)). ACP's delegated-payment spec models it as a single-use allowance and states that settlement, refunds, and chargebacks stay with the merchant and its PSP ([OpenAI Commerce spec](https://developers.openai.com/commerce/specs/payment)). Stripe's Sessions 2026 added the Machine Payments Protocol (stablecoins plus SPT-based fiat, co-authored with Tempo), a Link agent wallet with spending approvals, Smart Disputes, and an auto-resolving-disputes preview slated for Q4 ([Stripe](https://stripe.com/blog/everything-we-announced-at-sessions-2026)). Visa's Trusted Agent Protocol verifies RFC 9421 HTTP signatures from registered agents, bound to a merchant domain and operation, and defines no record of user intent ([visa/trusted-agent-protocol](https://github.com/visa/trusted-agent-protocol)); Visa's June 2026 announcements (Agent Score, an agent directory, stablecoin settlement at about a $7B annualized run rate) don't address intent capture or disputes either ([Visa, Jun 10, 2026](https://usa.visa.com/about-visa/newsroom/press-releases.releaseid.22491.html)).

**Intent-record standards match Readback and leave the hard part out.** AP2 v0.2 defines Checkout and Payment Mandates, open or closed, as SD-JWTs; in autonomous mode the open mandate must carry the agent's public key as `cnf` and the agent signs the closed mandates ([AP2 spec](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)). It specifies how to verify mandates and receipts in a dispute but places dispute resolution, retention, and retrieval outside its scope, and its FAQ imagines a card network as adjudicator ([AP2 FAQ](https://github.com/google-agentic-commerce/AP2/blob/main/docs/faq.md)). Mastercard's Verifiable Intent, Draft v0.1, is a three-layer chain: an issuer credential binding the user's device key, a user-signed mandate binding the agent key via `cnf`, and agent-signed final values for network and merchant; its repo says plainly, "Dispute resolution is explicitly out of scope" ([agent-intent/verifiable-intent](https://github.com/agent-intent/verifiable-intent)). Google contributed AP2 and Mastercard contributed VI to FIDO on Apr 28, 2026, with Mastercard and Visa chairing the payments working group and no deliverable dates ([FIDO Alliance](https://fidoalliance.org/fido-alliance-to-develop-standards-for-trusted-ai-agent-interactions/)). The crypto leg of AP2 is a separate A2A x402 extension at v0.1, and nothing fetched shows an x402 payment carrying an AP2 mandate ([a2a-x402](https://github.com/google-agentic-commerce/a2a-x402)). No live deployment of either standard verifying mandates in a real dispute was found.

Readback is VI's L2 and L3 on PayPal rails, with two honest gaps: VI's open mandate is user-signed and its constraints network-enforced, while Readback's open mandate is authenticated only by PayPal's approval page and its cap, item, and dates are enforced by the agent runtime and merchant gate. The closest thing to Readback's investigator view is GenLayer's "Internet Court," where five AI validators judge a MetaMask delegation's mandate against transaction evidence; it can constrain or revoke future authority but cannot reverse a settled payment unless an escrow was used, and no case has been published ([MetaMask](https://metamask.io/news/genlayer-internet-court-ai-agent-jury)). An AI jury deciding money is the opposite of Readback's first principle, so it is a differentiator, not a model.

## Stablecoin settlement is final, and recourse is the merchant's to give

A plain on-chain stablecoin transfer has no chargeback; PayPal's own crypto terms say external transfers are irreversible even while pending ([PayPal Cryptocurrency Terms, May 19, 2026](https://www.paypal.com/us/legalhub/paypal/cryptocurrencies-tnc)). Recourse exists only where it was built in before payment, and the live versions keep it with the merchant. Coinbase/Base's audited **Commerce Payments Protocol** mimics authorize-and-capture with void, reclaim, and refund, but the payer can only reclaim an expired, uncaptured hold ([base/commerce-payments](https://github.com/base/commerce-payments)). x402's **auth-capture** scheme v1.1 (Aug 18, 2026), built on that escrow, is explicit that charge, capture, void, and refund are not client-authorized; the payer's only unilateral move is reclaiming an untouched hold after the deadline ([x402 auth-capture](https://github.com/coinbase/x402/blob/main/specs/schemes/auth-capture/scheme_auth_capture.md)). After capture, "my AI bought that" is a request to the merchant, not a right against the rail. Designs with a neutral decision-maker remain research: Circle's Refund Protocol adds an arbiter but is unaudited and educational-only ([Circle](https://www.circle.com/blog/refund-protocol-non-custodial-dispute-resolution-for-stablecoin-payments)); x402r, ETHGlobal hackathon entries, and Kleros-style juries are early ([ETHGlobal](https://ethglobal.com/showcase/x402r-and-d-1k9yg); [Stanford Law](https://law.stanford.edu/publications/kleros-a-socio-legal-case-study-of-decentralized-justice-blockchain-arbitration/)); and the ADRP proposal, which splits disputes into cryptographically checkable and semantic classes, is an individual IETF draft ([draft-stone-adrp-01](https://www.ietf.org/archive/id/draft-stone-adrp-01.html)). Issuer freezes exist, but the GENIUS Act ties them to particular, reviewable court or agency orders, a law-enforcement channel rather than a consumer remedy ([Pub. L. 119-27](https://www.govinfo.gov/content/pkg/PLAW-119publ27/html/PLAW-119publ27.htm)).

Regulation adds no dispute right. The **GENIUS Act** (signed Jul 18, 2025; effective by Jan 18, 2027 at the latest) contains no error-resolution or unauthorized-transfer regime; it requires disclosed redemption policies, gives custody customers priority, and preserves state consumer law ([Pub. L. 119-27](https://www.govinfo.gov/content/pkg/PLAW-119publ27/html/PLAW-119publ27.htm); [Consumer Reports](https://advocacy.consumerreports.org/wp-content/uploads/2025/07/07-14-25-Consumer-Reports-Letter-Re-GENIUS-Act-S1582.pdf)). The CFPB's January 2025 proposal to bring stablecoin transfers under Reg E was **withdrawn on May 15, 2025**, and no 2026 CFPB action on agent payments was found ([Cogent Law](https://cogentlaw.com/stablecoin-payments-and-the-efta)). In the EU, e-money-token transfers that qualify as payment services must comply fully with PSD2 since Mar 2, 2026 ([Morgan Lewis](https://www.morganlewis.com/pubs/2026/02/eba-issues-supervisory-priorities-as-psd2-mica-transition-period-for-emt-activities-ends)); that plausibly brings PSD2's unauthorized-transaction refunds to custodial EMT transfers, but no source confirms it, and self-custodied wallets stay outside. Card networks still have no agent-specific reason code or liability shift ([Worldpay](https://www.worldpay.com/en/insights/articles/agentic-commerce-liability-is-still-being-written); [Chargeflow](https://www.chargeflow.io/blog/ai-agent-chargeback-liability)).

PayPal's crypto handling makes the Readback argument for it. Its crypto terms reimburse unauthorized transfers out of a Crypto Account up to a **$50,000 lifetime cap**, but exclude the case where the user gave someone authority and they exceeded it, until she notifies PayPal ([PayPal Cryptocurrency Terms](https://www.paypal.com/us/legalhub/paypal/cryptocurrencies-tnc)). That mirrors Reg E's rule that a transfer by someone the consumer authorized isn't unauthorized until notice ([12 CFR 1005.2(m)](https://www.consumerfinance.gov/rules-policy/regulations/1005/2/)). Purchase Protection is a separate program that excludes financial products ([PayPal Buyer Protection](https://www.paypal.com/us/legalhub/paypal/buyer-protection)), and a PYUSD send to an external wallet is a transfer, not a PayPal purchase, so it has no purchase-dispute path at all (inference; no PayPal document addresses it). On the agent side, PayPal's agentic commerce docs (updated Oct 14, 2026) describe Agent Ready and Store Sync without mentioning buyer authorization, PYUSD, or x402 ([PayPal Docs](https://developer.paypal.com/docsai/growth/agentic-commerce/overview)). PayPal's crypto lead called PYUSD a natural programmable layer for AI-native payments and said the industry still has to work out liability for bad agent purchases ([CoinDesk, May 10, 2026](https://www.coindesk.com/business/2026/05/10/agentic-commerce-will-run-on-crypto-rails-paypal-and-google-reps-tell-consensus-miami)). Treat a PYUSD agent rail as absent from PayPal's public material, not as confirmed never.

## Crypto keeps the grant after revocation; PayPal deletes it in minutes

The one place crypto is clearly ahead is durability. In Coinbase's contract, revocation sets a flag that is never cleared, a revoked permission can never be re-approved, and approval, revocation, and every spend each emit an event tied to the permission hash ([SpendPermissionManager.sol](https://raw.githubusercontent.com/coinbase/spend-permissions/main/src/SpendPermissionManager.sol)); anyone can reconstruct the full grant years later without Coinbase's help. MetaMask delegations live off-chain until first use, when the signed delegation lands on-chain in the redemption call; revocation is a separate on-chain `disableDelegation` ([MetaMask](https://docs.metamask.io/smart-accounts-kit/guides/delegation/disable-delegation/)). Even Safe's `deleteAllowance`, which clears state, leaves the original transaction in chain history. VI and AP2 mandates are portable signed objects the holder keeps.

Readback's grant lives only in PayPal. The spike measured PayPal deleting the agreement's payment token **about 3 to 30 minutes after an UNAUTHORISED claim**, twice (`docs/decisions/0001-sandbox-spike.md`, step 7; `docs/PROPOSAL-agent-terms.md`), after which only merchant-written copies remain and Readback withholds seller-favor suggestions. The crypto designs show the fix working in production: keep the grant, record revocation as a separate timestamped fact. That is exactly the proposal's `deleted_at`, and Reg E's notice rule makes the revocation time legally decisive. One more contrast cuts the other way: on-chain records are publicly verifiable, while Readback's checks need API access to the merchant's account, which is why `@readback/verify` and the "PayPal hosts it" argument matter.

## Conclusion

The field has quietly agreed on Readback's data model (user approval that pins an agent key, agent-signed purchases) and has equally quietly declined to own the dispute: AP2 and VI push adjudication to networks that have no rule for it, and stablecoin rails push it to the merchant who was paid. Readback's distinctive claim is therefore not the mandate but the evidence-and-suggested-verdict step for the adjudicator, on a rail that can still refund the buyer, including a suggestion against the merchant running it, and PayPal's own crypto terms show the scope-plus-revocation record is the fact that decides those cases.

The deletion finding reads differently against crypto. Inside PayPal's world it looks like a sandbox quirk; next to Coinbase's never-cleared revocation flag it looks like a design choice the rest of the industry made the other way. That turns the `agent_terms` proposal from a request into a catch-up, and it is the strongest framing available for it.

### Threats to the pitch, with one-sentence answers

1. **"Why not stablecoins plus smart-account spend limits?"** Limits stop out-of-bounds spends, but crypto's own dispute layer admits the hard case is the agent that stays inside them and still buys the wrong thing, and Readback suggests a verdict for that case from the signed record, on a rail where a refund still reaches her.
2. **"Networks already have agentic tokens and Verifiable Intent."** Tokens and TAP prove which agent presented a credential, and VI records intent but puts disputes explicitly out of scope; Readback supplies the evidence-and-suggested-verdict step they leave open, feeding PayPal's dispute process today.
3. **"Irreversibility is a feature: no chargebacks, no fraud."** Finality protects whoever got paid, including a merchant that charged with no request from her agent, which is exactly Readback's buyer-favor verdict.
4. **"Stripe SPTs already scope agent payments."** An SPT records a seller, a cap, and an expiry with no instruction and no agent key, so it can't tell an in-terms agent purchase from the merchant charging on its own.
5. **"PayPal will move agents to PYUSD anyway."** On-chain PYUSD sends have no purchase-dispute path and PayPal's terms make exceeded authority the user's problem, so a PYUSD agent rail would need the same scope-plus-signature record, and Readback's checks are rail-agnostic TypeScript over signed mandates (an inference, not a sourced claim).
6. **"x402 is backed by Visa, Mastercard, Google, and Stripe; PayPal isn't among its named supporters."** x402 carries a transfer signature, not an instruction, and has no dispute concept, so it doesn't compete for the problem Readback solves.
7. **"On-chain consent survives; yours is deleted."** Correct, and that's the headline of the `agent_terms` proposal: one retained field closes it.

### Where Readback is honestly weaker

| Dimension | Crypto or standard | Readback today |
|---|---|---|
| Durability of consent | On-chain grants and revocations are permanent; VI and AP2 mandates stay with the holder | PayPal deletes the agreement within minutes of an unauthorized claim |
| Enforcement point | Contract (Coinbase, ERC-7715) or network (VI) | Agent runtime and merchant gate; PayPal enforces only one charge per period and none after cancellation |
| Who signs consent | User-signed (VI L2, ERC-7715, Spend Permissions) | PayPal's approval page, which shows the plan name, not the stored terms (T21) |
| Key custody | Enclave behind a policy engine, or key shards | Env var in a plain service |
| Public verifiability | Anyone can read the chain | Needs API access to the merchant's account |
| Scope | Cross-merchant constraints (VI, AP2) | One merchant per agreement |
| Format | SD-JWT with selective disclosure | Compact JWS, no selective disclosure |
