# 0004 — Neutrality: one standard of evidence for buyers and sellers

Status: accepted (2026-10-15).

**Why this matters.** Readback is useful to PayPal only if PayPal can trust its suggestions in **both** directions. A tool that leans toward merchants is a dispute-defense product; one that leans toward shoppers would get turned off by merchants. Either way it's pointless for the party that adjudicates.

## Principles (each is enforced in code and covered by tests or evals)

1. **Outcomes rest only on things neither party can rewrite.** PayPal's objects (payment token, order, capture, dispute, the vault link), the terms the shopper approved on PayPal's page, and a signature by the agent key those terms name. Neither the buyer's statement nor the merchant's assertions decide anything. (`checks.ts`, THREAT-MODEL "design rule")
2. **The same rule protects whichever side it favors.** A request signed by her approved agent, inside her approved terms, delivered, with history → the evidence supports the **seller** (friendly fraud). A charge her agent never asked for, or outside her terms, or after she cancelled → the evidence supports the **buyer**. (`classify.ts` rows 2–4 and 8–13)
3. **Evidence a party controls can count against it, never for it.** The merchant runs the deployment and writes the labels, the terms copy and the tracker. So a merchant-written copy of the terms, or history that may still be lagging, can never be what earns a seller's-favor suggestion; it is shown, labeled "merchant-attested". Missing or contradictory merchant records still count against the merchant. This is a rule about who controls the evidence, not about sides: the buyer's own statements are treated as untrusted data for the same reason. (`applyModifiers` in `classify.ts`)
4. **No suggestion is a valid answer.** When the evidence can't separate the sides (a brand-new agreement with no history, contents "not as described", a shipment only the merchant reports), Readback suggests nothing and routes the case to PayPal review. "No suggestion" is never presented as a win for either side.
5. **Claude never rules, in either direction.** Claude's brief is rejected if any sentence suggests an outcome the deterministic classification didn't reach, toward the seller *or* the buyer (`brief.ts` validator, tested both ways). Dispute replies are generated by code from the checks (ADR 0003).
6. **Errors are measured both ways.** The evals report accuracy separately for cases the seller should win, cases the buyer should win and cases with no suggestion, and count wrong suggestions toward the seller *and* toward the buyer. Current: 5/5, 6/6, 4/4; 0 and 0 (`evals/results/latest.json`, also runnable at `/judge`).

## Known asymmetries, stated plainly

- **History threshold** (≥2 earlier undisputed charges, the earliest ≥7 days before): without it, an account-takeover approval would look exactly like a genuine one, so a disowned charge on a new agreement gets **no suggestion** rather than a seller's-favor one. That withholds a seller-side suggestion until the agreement has a track record; it doesn't hand the case to the buyer.
- **Tracker data is merchant-reported.** A missing tracker counts against the merchant on "not received"; a present one earns no suggestion by itself.
